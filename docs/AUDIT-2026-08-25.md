# Coterie — Complete Code & Architecture Audit

Date: 2026-08-25
Scope: full codebase — every math module, workflow, server action, database
table, RLS policy, auth gate, and the deploy pipeline.
Method: direct line-by-line reads of the security- and money-critical modules,
plus four parallel deep-dive passes covering (A) math, (B) workflows, (C) access
control, and (D) schema / RLS / deploy.

---

## 1. The headline (plain English)

**Coterie is architecturally sound and safe to keep running for clients.**

- **No critical or high-severity problems were found** anywhere — not in the
  money math, not in tenant isolation, not in the login/permission checks.
- **Tenant isolation is airtight.** All 36 client-data tables enforce database-
  level row security (a tenant physically cannot read another tenant's rows),
  and this matches the earlier live production spot-check (S11Z43d).
- **Every one of the 25 "server action" write paths checks who you are before
  it writes.** Nothing that touches a client's data runs without a login + an
  organization context.
- **The money math is correct and mostly unit-tested.** Division is guarded
  against divide-by-zero, dollars are handled with a precise decimal type, and
  date math uses calendar-correct boundaries.

The findings below are **refinements, not emergencies.** The most valuable one
(a clock that can be nudged backwards under an unusual sequence of events) is the
same *class* of bug we already fixed elsewhere in S11Z46 — this audit found two
more spots that were missed. None of these are client-visible failures today.

Think of this as a clean bill of health with a short punch-list.

## 3. The punch-list (prioritized)

Nothing here is a fire. They are ordered by how much they matter.

### MEDIUM — worth doing soon

**M1. "Last contacted" clock can move backwards in two spots.**
- Where: `src/lib/email/actions.ts` (`saveEmailThread`, ~line 385) and
  `src/app/dashboard/.../quick-capture-actions.ts` (`logQuickCapture`, ~line 222).
- What: When you log an email thread or a quick note, the app stamps the company's
  "last contacted" time — but unlike the Fireflies sync and the meeting logger,
  these two paths don't have the *forward-only guard*. If you back-date an entry,
  the company's clock can roll **backwards**, which can wrongly resurface a
  company in "Needs a Call."
- Why it matters: This is the exact bug we fixed in S11Z46 for meetings; two more
  paths were missed. Low blast radius, but it undermines the call clock the user
  specifically cares about.
- Fix shape: Add the same `OR: [{ lastContactAt: null }, { lastContactAt: { lt: <time> } }]`
  guard on both `updateMany` calls. This is the moment to extract a shared
  `touchLastContact` helper (now genuinely 4 call sites — the deferred S11Z46 note).

**M2. Soft-delete may not snapshot every child record it later needs.**
- Where: `src/lib/soft-delete.ts`.
- What: When a company is deleted, the app snapshots its action items using
  "company-owned OR contact-owned," but the pre-delete step only clears the
  contact-owned ones. A **staff-owned, company-linked** action item could either
  block the delete (database refusal) or cause a restore-time conflict.
- Why it matters: Delete/restore is a safety feature; it should never itself fail.
- Fix shape: Confirm the exact FK/`onDelete` behavior against the schema, then make
  the pre-delete set cover the same items the snapshot captures.

**M3. Auto-extraction failures are logged, not alerted; skipped meetings never retry.**
- Where: `src/lib/inngest.ts` (~line 99) and `src/lib/auto-action-items.ts` (~line 70).
- What: When post-sync action-item extraction fails or hits the AI rate limit,
  the error goes to `console.error` (invisible to the founder) and the affected
  meeting is silently skipped forever.
- Why it matters: This is the *silent background failure* class the S11Z43 Sentry
  work set out to kill — these two spots don't forward to Sentry, and there's no
  re-attempt.
- Fix shape: Forward these to Sentry (so they reach email), and let rate-limited
  meetings be picked up on the next sync instead of skipped permanently.

### LOW — defense-in-depth / polish

**L1. Two "introduction" foreign keys aren't tenant-composite.**
- Where: schema — `Introduction.partyAContactId` / `partyBContactId`.
- What: These point at contacts by plain id, not the tenant-composite
  `(id, orgId)` form used elsewhere. RLS already prevents cross-tenant reads, so
  this is not an isolation bug — but because these FKs are **required**, the
  composite form is fully expressible with zero downside and adds a second
  guardrail. (`contacts` already has the needed `@@unique([id, orgId])`.)
- Fix shape: A schema migration converting both to composite FKs.

**L2. A few other Cascade FKs are non-composite** (`Invoice`, `NewsItem`,
`Activity` → `companyId`). Same reasoning as L1; lower value.

**L3. Several child-record deletes use the member gate, not the admin gate.**
- Where: `deleteActionItem`, `removeInvitee`, `deleteNote`, `deleteCommitment`,
  `removeTeamMember`, and similar.
- What: These are RLS-scoped (no isolation risk) but let any staff member — not
  just admins — delete the record. This is a **policy choice**, not a bug. Decide
  whether staff should be able to delete these, or whether they should be
  admin-only like company/contact deletion.

**L4. Revenue "collection rate" reads 100% against $0 scheduled.**
- Where: `src/lib/revenue.ts` (~line 208).
- What: When nothing is scheduled yet, collection rate falls back to 100 ("100%
  collected" of nothing). Cosmetic; consider showing "—" instead.

**L5. "Due this month received" sums lifetime payments, not this-month payments.**
- Where: `src/lib/revenue.ts` (~line 200).
- What: A time-attribution mismatch — the figure labeled as this month's receipts
  actually sums all-time paid on this-month invoices. Verify the intended meaning.

**L6. `membersByRevenue.pct` is share-of-largest-member, not share-of-total.**
- Where: `src/lib/revenue.ts` (~line 243).
- What: It's used for bar scaling, so it's correct *for that purpose* — just a
  naming-clarity note so no one mistakes it for a percentage of total revenue.

**L7. LinkedIn enrichment has no row-claiming.**
- Where: LinkedIn enrich run.
- What: Two concurrent enrich runs could double-spend AI budget on the same rows.
  Unlikely in single-operator use today; worth a claim/lock before scaling.

**L8. `saveEmailThread` prospect dedupe is case-only.**
- What: It matches company names case-insensitively but doesn't use the fuller
  `normalizeCompanyName` (which also collapses whitespace), so "Acme  Inc" vs
  "Acme Inc" could fork. Minor.

### NIT — note and move on

- **N1. `value-created.ts` is the highest-value pure module without unit tests**
  (it contains a `networkMultiplier` division). Not wrong that we saw — but it's
  money math with no test net. Worth adding tests.
- **N2. Deploy doesn't auto-run migrations** (by design — a guardrail). The
  recurring footgun is shipping a migration-bearing slice without doing the DB
  step, which has caused prod 500s before. Keep the "after any migration slice,
  run `prisma migrate status` against prod" discipline.
